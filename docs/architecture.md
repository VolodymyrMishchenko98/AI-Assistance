# Архитектура AI-Assistance

**Статус:** архитектурное решение Modular Monolith + Clean Architecture
принято. Price Checker — единственный бизнес-модуль MVP. Архитектурные
границы и обязательные сценарии MVP зафиксированы; параметры реализации,
перечисленные в разделе «Параметры реализации для выбора/проверки», ещё не
выбраны или не проверены.

**Область документа:** архитектурное проектирование; код модулей и зависимости
пока не реализованы/не установлены.

**Целевая среда:** Windows, Lenovo IdeaPad Slim 5i, Intel Core i5-13420H,
16 ГБ RAM, интегрированная графика; CUDA не предполагается.

## Цели и ограничения

Приложение проектируется как локальный расширяемый модульный монолит. MVP
сосредоточен на Price Checker. Он должен помогать специалисту находить
доступные предложения и проверять их сопоставимость с позициями закупки, но
не должен автоматически одобрять договор или объявлять цену завышенной.

Документы и база остаются на компьютере пользователя. Внешнему поисковому
провайдеру передаётся только запрос, необходимый для поиска товара; это всё
равно может раскрывать сведения о закупке. Перед отправкой запроса интерфейс
должен показывать и минимизировать передаваемые данные. Облачные AI API,
платный поиск, обход CAPTCHA, авторизации, платного доступа и иных технических
ограничений не являются частью архитектуры.

## Архитектурные слои

| Слой | Ответственность | Не должен зависеть от |
|---|---|---|
| Domain | Сущности, value objects, инварианты, доменные правила | Веб-фреймворков, ORM, сетевых клиентов, файловой системы и внешних провайдеров |
| Application | Сценарии использования, команды и запросы, координация портов, DTO | Конкретных инфраструктурных реализаций |
| Infrastructure | SQLite, миграции, поисковые и страничные адаптеры, файловое хранилище, OCR/AI-адаптеры | Presentation |
| Presentation | HTTP API, интерфейс, валидация входа и сериализация ответа | Внутренних деталей Infrastructure |

Направление зависимостей:

```text
Presentation ──► Application ──► Domain
Infrastructure ────────────────► Application ports
Infrastructure ────────────────► Domain (только для преобразования моделей)

Bootstrap / composition root ──► Presentation, Application, Infrastructure
```

`Domain` не импортирует FastAPI, SQLAlchemy, HTTPX, SQLite, шаблоны UI или
провайдеров. Application определяет порты, нужные конкретным сценариям;
Infrastructure реализует их. Единственная точка, где связываются интерфейс
порта и реализация, — composition root. Автоматический DI-контейнер не нужен,
пока явная сборка зависимостей остаётся простой.

## Price Checker MVP и поток данных

Позиции добавляются в черновик запуска вручную или из `.xlsx`. MVP не
разбирает договоры и не выполняет OCR. Это отдельная будущая ответственность
Document Intelligence, а не скрытая часть Excel-импорта.

## Модель доверия и изоляция импортных операций

Текущий локальный MVP не имеет пользовательских аккаунтов, сессий или
авторизации. HTTP-сервер привязан к loopback и рассчитывает на то, что доступ
к процессу приложения уже ограничен локальной ОС. Это не аутентификация:
любое локальное лицо, которое может вызвать HTTP handler или прямой
Application API, считается доверенным оператором приложения.

Тем не менее операция импорта однозначно привязана к `run_id` на уровне базы
и Application: preview/row/edit/exclude/confirm проверяют совпадение
`import_operations.run_id` с переданным ReviewRun. Это предметная изоляция
данных, но не замена будущей аутентификации. При появлении пользователей
требуется явная subject/session-policy и проверка права доступа к run.

Поток создания проверки:

1. Специалист создаёт черновик запуска и вручную добавляет одну или несколько
   позиций либо загружает `.xlsx`.
2. Для `.xlsx` специалист выбирает лист и строку заголовков, сопоставляет
   колонки полям позиции и просматривает строки до подтверждения. Предпросмотр
   показывает отчёт с числом валидных/невалидных строк, ошибками и
   предупреждениями с номером строки и полем. Невалидную строку можно
   исправить или явно исключить; она не импортируется молча.
3. Подтверждённые строки добавляются в черновик. До старта проверки их можно
   редактировать, удалять и дополнять вручную. Запуск поиска доступен после
   явного действия специалиста; при старте версия каждой позиции
   фиксируется для этого запуска.
4. Application валидирует и сохраняет позиции короткой транзакцией, создаёт
   задания поиска и фиксирует идентификатор операции импорта для защиты от
   повторной отправки формы.
5. Use case генерирует несколько поисковых запросов из подтверждённых полей.
   Неизвестные производитель, модель и характеристики не дополняются догадками.
6. SearchProvider возвращает URL-кандидаты и метаданные провайдера.
   Результат поиска — только наводка, не подтверждение цены.
7. Проверка политики источника решает, разрешено ли извлекать страницу.
   ProductPageExtractor возвращает извлечённые наблюдения с происхождением
   каждого поля.
8. Application нормализует доступные единицы и запускает правила
   сопоставления. Domain правила не обращаются к сети и базе данных.
9. Результат, неизвестные поля, источники и ошибки сохраняются независимо
   по каждой позиции. Специалист может исправить характеристики и подтвердить
   или отклонить сопоставимость.
10. ReportExporter формирует отчёт из подтверждённых данных, наблюдений,
    решений специалиста и явно отмеченных пробелов.

Автоматический поиск товаров через бесплатные разрешённые источники —
обязательное требование MVP. Конкретный поисковый провайдер/источник пока не
выбран. Если автоматический поиск временно недоступен, используется резервный
сценарий: специалист вручную вставляет URL, после чего страница анализируется
по тем же правилам. Полный разбор
договоров, OCR, Contract Checker и AI-помощники не считаются частью MVP.
Excel-импорт является входным сценарием самого Price Checker, а не разбором
произвольных документов. Принимается `.xlsx`; другие форматы, включая
`.xlsm`, не входят в MVP. Книга открывается только для чтения; формулы не
исполняются, а формульные значения без доступного статического значения
помечаются для исправления/проверки. Колонки сопоставляются явно, а не
угадываются по похожим заголовкам. Минимально требуется наименование
позиции; остальные поля и ограничения определяются версионированной
политикой проверки. В предпросмотре фиксируются исходная строка, результат
валидации и применённое сопоставление колонок.

Предпросмотр импорта — временный DTO и не создаёт позиций в базе. При
подтверждении валидные и исправленные строки сохраняются как редактируемые
позиции черновика. Повтор той же операции подтверждения с тем же
idempotency key возвращает ранее созданные позиции, а не добавляет дубликаты.
Точные совпадения строк в одной книге показываются как предупреждение, но не
сливаются автоматически: одинаковые позиции могут быть разными строками
закупки с разным количеством или условиями. Специалист может оставить их
раздельными или явно удалить лишнюю строку до запуска.

### Обработка очереди

Очередь и статусы заданий хранятся в SQLite; несколько запусков могут
обрабатываться одновременно в одном процессе приложения. Каждый запуск,
позиция и task имеют собственный ID и внешние ключи. Для MVP предполагается
один экземпляр приложения; это исключает конкурирующие локальные пулы workers.
Уникальный ключ задания `(run_id, item_id, operation, generation)` запрещает
создать второй task для той же позиции, операции и поколения независимо от
статуса task. Повторная отправка команды защищается idempotency key.
Технические retry увеличивают счётчик попыток существующего task; явный
повтор поиска создаёт новое поколение и сохраняет предыдущие наблюдения.

Одинаковые описания у разных строк — не основание объединять позиции.
Сохраняются разные `item_id`, поиск и результат на каждую строку; в предпросмотре
можно показать предупреждение о возможном дубликате. При повторной отправке
той же позиции с тем же ID в рамках того же запуска use case возвращает
существующую позицию/задачу. Повторная задача создаётся только явным
действием «повторить поиск». После старта версия спецификации позиции
заморожена; изменение исходных требований требует новой версии позиции и
явного повторного запуска, а не незаметного изменения входа уже выполняемой
проверки.

Число workers настраивается централизованно и ограничивается верхним пределом.
Стартовое предложение для проверки на Lenovo — два параллельных задания и
жёсткий локальный предел четыре; лимиты конкретного провайдера или домена
могут быть ниже. Это параметры для измерений, а не обещание целевой
производительности.

Изменение статуса/назначение lease выполняется короткой транзакцией. Worker
фиксирует claim и закрывает транзакцию до сетевого запроса; HTTP, ожидание
повтора и разбор ответа не выполняются внутри транзакции. Полученный результат
сохраняется отдельной короткой транзакцией. Транзакция импорта может пакетно
сохранить подтверждённые строки, но не выполняет поиск или обработку файлов
во время блокировки БД. Настройки SQLite (busy timeout, WAL) выбираются и
проверяются под фактическую конкурентную нагрузку.

У задания позиции есть собственный статус, число попыток, время начала и
ошибка без текста договора. Остановка запуска запрещает новые запросы этого
запуска, отменяет ожидающие задачи и запрашивает кооперативную отмену активных
операций; уже записанные результаты сохраняются. После перезапуска истёкшие
leases и незавершённые задачи переводятся в ожидающие/прерванные с явным
статусом и могут быть безопасно повторены. Запись результата идемпотентна по
task attempt/source observation, а каждое новое получение предложения
добавляет новую ценовую observation, не затирая старую. Ошибка одного запуска
или позиции не отменяет другие.

## Договор сопоставления

Результат — одно из значений: «сопоставимо», «требуются уточнения»,
«не сопоставимо». Обоснование перечисляет совпавшие поля, существенные
противоречия и отсутствующие сведения. Отсутствие значения не считается
совпадением.

Сравниваются производитель и модель, размеры, мощность, материалы,
комплектация, технические параметры, единицы, количество в упаковке,
условия поставки, НДС и доставка. Нормализация не уничтожает исходный текст.
Цену за упаковку нельзя сравнивать с ценой за единицу, пока достоверно
неизвестно количество в упаковке. Если валюта, налог, доставка, наличие
или единица цены неизвестны, система указывает это и при необходимости
возвращает «требуются уточнения».

Числовая схожесть, если она появится, остаётся поясняющей подсказкой и не
заменяет категорию. Пороговые значения и обязательные поля должны быть
настроены после проверки на реальных обезличенных примерах. Ни одна
категория не является юридическим или закупочным решением.

## Данные и происхождение

Слои данных разделены логически:

- **Original source data:** исходное наименование позиции, URL страницы,
  исходный текст доступного поля; документ — локальная ссылка и хеш, если
  документ обрабатывается.
- **Normalized data:** нормализованные производитель, модель, параметры,
  единицы, валюта и количество с сохранением исходника.
- **Extracted observations:** найденные значения, источник, время, способ
  извлечения, место/фрагмент страницы при возможности и уверенность
  извлечения.
- **Validation results:** проверенные ограничения и результат сопоставления.
- **Human decisions:** подтверждения/исправления специалиста, автор и время.
- **Audit history:** значимые переходы статусов и изменения решения без
  записи полного текста договора.

Основные Domain-модели Price Checker:

- `ReviewRun` — запуск проверки, профиль/снимок правил, даты и общий статус.
- `ProcurementItem` — позиция, исходное описание, подтверждённые требования
  и статус обработки.
- `ProductSpecification` — value object нормализованных характеристик с
  единицами; не заменяет исходный текст позиции.
- `OfferObservation` — неизменяемый снимок полученного предложения, seller,
  исходного названия, характеристик и коммерческих условий с provenance.
- `ObservedFact` — извлечённое значение конкретного поля и provenance;
  observation не становится подтверждённым требованием автоматически.
- `MatchAssessment` — категория сопоставимости и объясняющие причины.
- `HumanDecision` — решение специалиста и ссылка на оценку, которую он
  подтвердил или исправил.
- `ReviewPolicySnapshot` — неизменяемые версия и данные правил, применённые
  к одному запуску; для MVP используется утверждённая базовая политика.

Application DTO отдельны от Domain: `CreateReviewRunCommand`,
`ImportItemsCommand`, `SearchQuery`, `SearchResult`, `PageExtractionResult`,
`ReviewProgressDto`, `MatchAssessmentDto` и `PriceCheckReportDto`. DTO
представления валидируются и сериализуются на границе Presentation; структуры
ORM существуют только в Infrastructure. Это не один универсальный объект,
передаваемый без преобразования через все слои.

Предварительные таблицы MVP: `review_runs`, `contract_items`,
`search_tasks`, `search_queries`, `sources`, `offer_observations`,
`field_observations`, `match_assessments`, `human_decisions`, `audit_events`.
В `review_runs` сохраняются версия и неизменяемый snapshot политики, поэтому
изменение будущего профиля не меняет завершённый или запущенный review.
Профили заказчиков и документы не принадлежат схеме Price Checker. SQLite
схема и миграции находятся только в Infrastructure и создаются с первой
версии. Domain-модели не являются ORM-моделями или API-схемами.

### История цен и идентичность товара

Каждое получение страницы создаёт новую append-only `OfferObservation` с
собственным ID, `observed_at` (время получения), исходным URL и полями,
которые удалось извлечь: продавец, название, характеристики, цена, валюта,
НДС, доставка и доступность. Для цены хранится исходное значение и
нормализованное значение, если нормализация достоверна. НДС/доставка могут
иметь состояния «включено», «не включено», «не указано» или «не удалось
проверить». Источник и время фиксируются для каждого факта; даты,
опубликованные продавцом, сохраняются отдельно и не подменяют время
получения.

Observation никогда не обновляется поверх предыдущей. Повторное получение
той же страницы — новая observation. Связь `repeat_of`/«обновление того же
объявления» допускается только при достоверном стабильном идентификаторе
листинга от источника либо ручном подтверждении и не означает, что это тот же
физический товар. Изменение цены у того же подтверждённого листинга — новая
observation со связью на предыдущую, а не UPDATE старой записи. Для ясности
хранится отношение к предыдущему наблюдению (`first_seen`,
`same_listing_repeat`, `same_listing_changed`) и основание связи; последнее
значение допускается только если источник подтверждает идентичность листинга.
Это не присваивает идентичность самого товара.

В MVP нет канонического каталога товаров и аналитического модуля. Совпадение
URL, продавца, текста или нормализованного названия само по себе не доказывает
идентичность товара. Если существенных доказательств мало, observations
остаются отдельными, а связь отмечается как неизвестная/кандидатная.
Будущая история цен сможет строиться по временным observations и отдельным
подтверждённым связям идентичности, не переписывая первичные записи.

### Будущие профили и версии политики

Будущий модуль Customer and Procurement Profiles владеет данными профиля:
заказчиком, категориями закупок, дополнительными обязательными
характеристиками и декларативными правилами валидации для категорий. Правила
ограничиваются версионируемым набором поддерживаемых условий, а не
исполняемым кодом заказчика.

Для старта проверки Price Checker получает через Application-контракт
неизменяемый `ReviewPolicySnapshot` DTO (идентификатор профиля, версия,
категории, обязательные поля, ограничения и версия схемы), проверяет его и
сохраняет собственную копию/хеш вместе с `ReviewRun`. Цена конкретного
запуска оценивается по этому снимку. Price Checker не читает таблицы будущего
модуля профилей и не зависит от его ORM или репозитория. Обновление профиля
создаёт новую версию для будущих запусков; старые снимки и результаты
неизменны. Пока модуль профилей не создан, используется версия базовой
политики Price Checker.

Репозиторные порты должны быть узкими и соответствовать агрегатам/сценариям,
например `ReviewRunRepository` и `OfferObservationRepository`; один универсальный CRUD
репозиторий не вводится. SQLite WAL можно рассмотреть после проверки
конкурентных сценариев и резервного копирования.

## Порты и DTO

Контракты принадлежат Application-слою использующего их модуля. Ниже описаны
сигнатуры на уровне архитектуры, а не требование создавать сейчас пустые
Python-классы. DTO на входе и выходе не являются Domain-сущностями или
ORM-моделями.

| Порт | Вход | Результат и ошибки |
|---|---|---|
| `SearchProvider.search` | `SearchQuery`: текст, локаль, предел результатов и correlation ID | `SearchResult`: кандидаты URL, провайдер и время; typed failure для лимита, временной ошибки и постоянного отказа |
| `ProductPageExtractor.extract` | `SearchCandidate` и применённая `FetchPolicy` | `PageExtractionResult`: источник и наблюдения полей с provenance; typed failure для запрещённого доступа, неподдерживаемой страницы и временной ошибки |
| `StorageRepository` | Контракт роли сохранения данных проверки | Не один общий интерфейс: отдельные порты вроде `ReviewRunRepository`, `OfferObservationRepository` и `HumanDecisionRepository` с операциями нужных use cases |
| `ReportExporter.export` | `PriceCheckReportDto` и выбранный формат/назначение | `ExportResult` с путём/метаданными созданного отчёта либо явной ошибкой экспорта |
| `DocumentParser.parse` | `DocumentReference` и параметры извлечения | `ParsedDocumentDto`: исходные фрагменты, кандидаты позиций, неопределённость; принадлежит будущему Document Intelligence |
| `OCRProvider.recognize` | Ссылка на локальную страницу документа и языковые подсказки | `OcrPageResult`: текст, координаты фрагментов, язык/качество и время; принадлежит будущему Document Intelligence |
| `AIProvider.suggest_product_attributes` | Минимизированное описание товара и разрешённые поля | `AttributeSuggestionsDto` с provenance/моделью и неопределённостью; только будущая локальная подсказка, не решение |

Названия `SearchQuery`, `SearchResult`, `SearchCandidate`,
`PageExtractionResult`, `PriceCheckReportDto` и остальных DTO фиксируют
границы данных. Реализация определит конкретные типы и правила сериализации
после утверждения сценариев. Ошибки портов возвращаются явно; они не
превращаются в пустой список и не маскируются под успешный результат.
Cancellation передаётся use cases в длительные операции, чтобы остановка
задания не запускала новые сетевые запросы.

В composition root конкретные реализации передаются use cases явными
аргументами конструктора/функции. Presentation зависит от Application API,
а не от репозиториев и адаптеров. Контрактные тесты портов запускаются на
каждом реализованном адаптере.

## Поиск и внешние ограничения

`SearchProvider` — заменяемый адаптер, а не зависимость на конкретный магазин.
Для каждого провайдера настраиваются допустимые запросы, лимиты, тайм-ауты
и статус доступности. `ProductPageExtractor` не обходит CAPTCHA, авторизацию,
платный доступ, блокировки или иные технические ограничения. Проверяются
условия сайта и правила автоматического доступа; `robots.txt` не является
самостоятельным юридическим разрешением.

На дату проектирования универсальный бесплатный поиск не гарантирован:
Google Custom Search JSON API закрыт для новых клиентов и должен прекратить
работу 1 января 2027 года; Bing Search APIs прекращены 11 августа 2025 года.
Поэтому автоматические провайдеры утверждаются отдельно, а ручной режим
остается штатным резервом. Источники:
[Google Custom Search API](https://developers.google.com/custom-search/v1/overview),
[объявление Microsoft о выводе Bing Search APIs](https://learn.microsoft.com/en-us/lifecycle/announcements/bing-search-api-retirement),
[RFC 9309](https://www.rfc-editor.org/rfc/rfc9309).

Внешней странице нельзя доверять как исполняемому содержимому. Загрузка
ограничивается схемами HTTP(S), размерами, типами контента, временем и
числом перенаправлений; защищаются локальные и приватные сетевые адреса
(SSRF). Не логируются текст документов, поисковые запросы целиком,
персональные сведения и содержимое страниц.

## Кандидаты по технологиям

Выбор библиотек откладывается до утверждения границ MVP. Возможные кандидаты:

| Задача | Кандидат | Почему подходит | Ограничения |
|---|---|---|---|
| Локальный API | FastAPI | Типизированные запросы и локальный HTTP API | Не должен проникать в Application/Domain |
| Интерфейс MVP | Jinja2 + HTMX | Нет отдельной сборки фронтенда, достаточно для таблиц и форм | Менее гибок для сложного интерактивного UI |
| Импорт `.xlsx` | openpyxl в read-only режиме | Чтение листов/ячеек без исполнения формул; достаточно для пакетного импорта | Только `.xlsx`; проверять размеры книги, формулы не вычисляются |
| HTTP | HTTPX | Тайм-ауты, тестируемый клиент, асинхронные запросы | Нужны строгие лимиты и контролируемая отмена |
| HTML | BeautifulSoup; при необходимости lxml | Локальный разбор HTML | Нет гарантии работы с динамическими страницами |
| База | SQLite; SQLAlchemy в Infrastructure | Локальная работа без сервера и SQL-модели вне Domain | Один пользователь/локальная нагрузка; миграции обязательны |
| PDF/DOCX в будущем | PyMuPDF, python-docx | Локальное извлечение текста | Сканам нужен OCR; проверить лицензирование и качество документов |
| OCR в будущем | Tesseract | Бесплатная локальная обработка на CPU | Дополнительная установка, языковые данные, качество скана и CPU-время |
| Проверка | pytest и сетевые моки | Повторяемые тесты без зависимости от внешних сайтов | Не заменяют интеграционную проверку на Lenovo |

Ни одна AI-модель не обязательна для MVP. Если в будущем AI используется для
извлечения или подсказок, результат считается непроверенным наблюдением,
требует происхождения и человеческого подтверждения. Он не принимает решений
о сопоставимости или договоре.

## Конфигурация, ошибки и логирование

Параметры приложения централизованы: пути хранения, допустимые провайдеры,
лимиты параллельности, тайм-ауты, повторные попытки, максимальный размер
загрузок и политика хранения. Секреты, если появятся, не хранятся в Git.

Ошибки классифицируются по позиции/источнику: временная сеть, постоянный
отказ, ограничение доступа, неподдерживаемый формат, ошибка извлечения,
отмена. Пользователь получает понятный статус; логи — идентификатор задания,
код ошибки и технический контекст без содержимого договора. Успешный пустой
результат не используется как маска ошибки.

## Тестирование и критерии готовности

- Unit-тесты Domain проверяют правила и нормализацию без БД/сети.
- Тесты Application используют фейки портов для сценариев ошибки, повтора,
  отмены и частично выполненного договора.
- Контрактные тесты проверяют соответствие адаптеров портам.
- Интеграционные тесты используют временную SQLite и локальные HTML/PDF
  фикстуры; реальные поисковые сайты не вызываются в обычном тестовом наборе.
- Тесты импорта проверяют сопоставление колонок, предпросмотр, исправление,
  ошибки/исключение строк, дубликаты и идемпотентное подтверждение.
- Конкурентные тесты запускают несколько review runs одновременно, проверяют
  короткие DB-транзакции, уникальность задач, отмену, lease recovery и
  отсутствие потери observations.
- На Lenovo проверяются установка с чистого клона, импорт и обработка
  100+ позиций, параллельные запуски, отмена, восстановление, пиковая RAM
  и время. Измеряется также поведение SQLite под настроенным пределом workers.

MVP готов к использованию только после проверки, что результаты содержат
источник и время, неизвестные сведения не выдумываются, сбой позиции не
теряет результаты остальных, а окончательное решение остаётся за специалистом.

## Параметры реализации для выбора/проверки

1. Конкретный разрешённый бесплатный автоматический поисковый провайдер/источник
   и его ограничения. Сам автоматический поиск является обязательным сценарием
   MVP; ручная вставка URL — только резервный сценарий недоступности поиска.
2. Набор колонок и правил валидации для `.xlsx`, лимиты размера книги и
   политика хранения источников/фрагментов страниц.
3. Формат итогового отчёта и поля, существенные для сопоставления.
4. Схема декларативной версии `ReviewPolicySnapshot` для будущих профилей.
5. Стартовый предел workers (предлагается 2, предел 4) и измеримые цели
   времени/RAM на Lenovo.
6. Утверждение локального браузерного интерфейса и библиотек базы/миграций.
